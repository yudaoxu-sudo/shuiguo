# 抖音数据来源切换决策记录（2026-07）

状态：**继续观察，生产保持网页版主源**。本文档汇总项目内记录与已核验的生产双源
结果，用于支撑"是否把正式月报的抖音来源从网页版切换为聚合接口版"的决定；
文档本身不改变任何生产行为。

## 1. 背景与范围

- 正式月报的抖音线上营业额有两条读取来源。二者共用同一份抖音来客登录态存储，
  读取同一个账单统计页面的本月聚合数据，均不主动退出或重新登录，
  均不读取逐笔订单或账单明细（两个读取器代码中均无开放平台逐笔明细请求路径）。
- 来源由环境变量 `DOUYIN_SOURCE` 选择（`scripts/read-current-douyin.cjs`）：
  未设置时默认 `browser`（网页版）；设为 `aggregate-api` 时改用聚合接口版；
  其他值直接报错。环境变量配置模板目前未收录该变量。
- 本任务不读取本地或服务器生产配置，不联网，因此未核实生产环境当前是否设置过
  `DOUYIN_SOURCE`；若生产未设置该变量，按代码默认值主源为网页版。
- 本任务不修改生产配置、cron、报告代码，不部署、不提交、不推送。

## 3. 两源对比表

| 维度 | 聚合接口版（`aggregate-api`） | 网页版（`browser`） |
| --- | --- | --- |
| 实现文件 | `scripts/read-current-douyin-aggregate-api.cjs` | `scripts/read-current-douyin-browser.cjs` |
| 结果 `source` 标识 | `douyin_life_finance_aggregate_api` | `douyin_life_finance_summary` |
| 读取方式 | 打开账单页拿到页面自身请求的模板参数后，在页面内直接请求两个聚合接口各一次：本月到账汇总 `query_date_statistics`、本月门店汇总 `query_statistics` | 打开账单页后模拟操作：选"本月"、切"按日期"读结算状态表、切"按门店"读门店表，并从页面文本抓"商家应得"总额 |
| 金额精度 | 接口返回整数分（`income`、`settled_income`），`integerCents` 强制校验安全整数 | 页面"元"字符串解析为分（`moneyToCents` 四舍五入） |
| 预计到账口径 | `商家应得 − 已结算`（接口字段直接相减） | 按日期表中"待结算"行求和，再反推实际到账 |
| 完整性校验 | 本月汇总必须恰好 1 行；金额非负；门店分页必须一次读全（`page_count`/`total_count` 校验）；总额与门店合计相差 ±1 分以内视为舍入容差，总额高出超过 1 分记"未归属门店"，门店合计高出超过 1 分报错 | 待结算日期不得超出当前可见页；门店页必须有证据证明已读完整；门店残差采用同一套 ±1 分舍入容差和超额规则 |
| 页面依赖 | 仍需账单页加载成功以获得会话和模板请求，但不依赖页面渲染出的汇总表与控件 | 完全依赖页面控件与表格结构（"本月"、"按日期"、"按门店"、表头文案） |
| 主要失效风险 | 接口路径、参数或字段改版；模板请求捕获失败（有 30 秒等待加一次刷新兜底） | 页面结构或文案改版；表格分页；控件定位失败；文本金额解析歧义 |
| 请求负载 | 页面自身加载 + 2 次汇总请求；不消耗开放平台逐笔账单额度 | 页面自身加载 + 多步 UI 操作与等待 |
| 登录失效表现 | 检测到 `/p/login` 即报"抖音来客登录态失效"（两侧相同文案） | 同左 |
| 失败调试产物 | 调试目录全页截图 | 调试目录全页截图 + 页面正文文本 |
| 当前角色 | 备选源，需显式 `DOUYIN_SOURCE=aggregate-api` | 默认主源（`DOUYIN_SOURCE` 未设置时） |

两侧输出结构完全同构（`settlement` 三项 + `stores` + 残差处理一致），下游报表、
测试与告警不感知来源差异。

## 4. 现有双源核对机制

- 服务器生产配置设 `DUAL_DOUYIN_REPORT_DATE=YYYY-MM-DD` 后，当天夜间
  `report:scheduled` 改跑 `send-dual-douyin-report.cjs`，发送两份完整报告
  （"聚合接口版"与"网页版"）。聚合接口版先生成，网页版随后生成并复用同一份
  芝麻地、乐檬快照，只更换抖音来源。
- 两份报告头部附核对结论：本月总额、已到账、预计到账的逐项差
  （聚合接口 − 网页）、存在差异的门店家数（逐门店差额存于状态文件的
  `comparison.store_differences`），以及两次读取相隔秒数；存在差异时明确提示"期间抖音数据
  可能更新"（`scripts/send-dual-douyin-report.cjs`）。
- 幂等：两份都成功才记当天任务完成；单份成功会写入双源核对状态文件
  （含 `sentAt`、`sha256`、钉钉返回），补跑不重复发送。
- 双报告日期，白天 `report-healthcheck`（cron `17 9-21/3`，即 09:17 至 21:17
  每 3 小时）会用 `NO_DINGTALK=1` 同时预检两条来源，失败走"水果店报表预检失败"
  告警（`scripts/check-report-health.cjs`）。

## 5. 切换为聚合接口主源的判据

以下条件全部满足时，才建议把主源切换为聚合接口版。核对材料位于服务器部署目录
的运行时状态产物中：双源核对状态文件、两份双报告存档、两条来源的抖音月度快照、
调试截图，以及白天预检日志。阈值为建议值，采用与否由用户确认。

1. **双源一致**：至少 3 个双报告核对日（建议覆盖月中与月末各一次），
   `comparison.exact` 为 `true`；或差异仅出现在当天待结算方向、金额量级与
   `read_gap_seconds` 读取时差内的实时经营更新相称，且门店归属差异为零。
2. **无法解释的差异为零**：任何一次核对出现无法用读取时差解释的总额、已到账
   或门店差异，判据即不成立，需先查明原因。
3. **预检全绿**：核对期内双报告日期的白天预检没有触发"水果店报表预检失败"
   告警（同一问题有 1 小时冷却，不会因冷却漏报持续故障）。
4. **聚合接口自身稳定**：核对期内聚合接口版没有触发其数据断言（本月汇总行数
   异常、非整数分、负数、门店分页未读全、门店合计超总额超过 1 分）。
5. **口径关系成立**：聚合结果满足 README 三组关系——实际到账 + 预计到账 =
   本月商家应得；门店商家应得合计 + 未归属金额 = 本月商家应得；金额均为
   平台扣点后金额，不再重复扣 2.5%。
6. **登录态无副作用**：核对期内 `login-healthcheck` 与抖音登录态未因聚合请求
   出现异常（聚合版与网页版共用登录态，均不主动退出）。

用户决定切换后的执行方式（本任务未执行）：在服务器生产配置增加
`DOUYIN_SOURCE=aggregate-api`；重启 `fruit-store-listener.service` 使 `@666`
实时报采用新值（原因见第 7 节第 3 步）；随后按 runbook 用
`NO_DINGTALK=1 REPORT_FAILURE_ALERTS=false pnpm report` 做一次不推送的全链路
预演，确认输出 JSON 的 `source` 为 `douyin_life_finance_aggregate_api`。

## 6. 网页版回退与审计条件

网页版保留为回退通道：代码与 `pnpm douyin:monthly` 入口不删除，
`read-current-douyin.cjs` 的默认分支保持 `browser`。

切换后出现任一情形即回退网页版（按第 7 节步骤执行）：

- 聚合接口版连续 2 个报表日失败，或触发第 5 节第 4 条所列任一数据断言；
- 双源审计核对出现无法用读取时差解释的金额或门店差异；
- 抖音接口路径、参数或字段改版导致聚合读取不可用，而网页版预检可通过；
- 收到"水果店月度报表最终失败"告警且失败原因指向聚合接口读取。

切换后的审计条件：

- 定期（建议每月至少一次）设置 `DUAL_DOUYIN_REPORT_DATE` 跑双报告核对日，
  白天双预检与夜间双报告照常执行；
- 审计记录以双源核对状态文件（每份含 `sentAt`、`sha256`、`comparison`）
  与两份双报告存档为准，保留备查；
- 出现差异时先对照 `read_gap_seconds` 与当日经营时段判断是否为实时更新所致，
  不能解释的差异按上文回退条件处理。

## 7. 回滚步骤

回滚只改一个环境变量，不改 cron、不改代码、不删聚合脚本：

1. 在服务器部署目录的生产配置中删除 `DOUYIN_SOURCE=aggregate-api` 一行
   （或改为 `DOUYIN_SOURCE=browser`）。按 runbook 安全要求，操作中不打印
   生产配置内容。
2. cron 任务（`report:scheduled`、`report-healthcheck`）每次运行都是新进程、
   现场读取生产配置，改完即对下一次运行生效，无需额外操作。
3. 重启监听服务：`sudo systemctl restart fruit-store-listener.service`。
   原因：`listen-dingtalk.cjs` 启动时把生产配置读入自身进程环境并原样传给
   报表子进程，而 `daily-report.cjs` 的 `loadEnv` 不覆盖已存在的环境变量；
   不重启则 `@666` 实时报仍沿用监听启动时的旧值。
4. 按 runbook 验证：`systemctl is-active fruit-store-listener.service`、
   `pnpm healthcheck`、`pnpm login-healthcheck`，再用
   `NO_DINGTALK=1 REPORT_FAILURE_ALERTS=false pnpm report` 做不推送预演，
   确认输出 JSON 的 `source` 回到 `douyin_life_finance_summary`。
5. 保留回滚前的调试截图与运行时状态文件备查，便于事后分析聚合接口
   失败原因。

## 8. 失败告警保持不变

告警逻辑全部位于抖音来源抽象之上，只感知 `readDouyin` 抛出的错误，不感知
`DOUYIN_SOURCE` 取值。切换或回滚都不修改任何告警文案、阈值、冷却或推送渠道：

- `daily-report.cjs`：抖音读取失败先走 `retryStep`（登录失效立即中止，其余错误
  默认重试 3 次）；最终失败且 `REPORT_FAILURE_ALERTS` 未禁用时推送
  "水果店月度报表失败"（带 @ 告警）。正式月报失败即停止，不推送缺少线上
  营业额和毛利的残缺报表——两条来源同样适用。
- `run-scheduled-report.cjs`：夜间 22:05 起每 15 分钟补跑，全部失败只在 23:50
  最终轮推送一次"水果店月度报表最终失败"。双报告日期同样由它调度，最终告警
  行为一致。
- `check-report-health.cjs`：白天预检失败推送"水果店报表预检失败"，同一问题
  1 小时冷却；等待芝麻地验证码的状态不告警。
- 监听心跳告警（`healthcheck`，3 分钟无心跳）与登录健康告警
  （`login-healthcheck`）与抖音来源无关，保持原样。
